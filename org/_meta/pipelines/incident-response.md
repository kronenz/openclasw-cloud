# incident-response 파이프라인

## 개요
장애 감지부터 복구, 고객 안내, 포스트모템까지 전체 인시던트 대응 프로세스를 관리하는 파이프라인.

**담당 팀**: Operations Team
**평균 소요 시간**: 즉시-30분 (자동 복구), 1-2시간 (수동 복구)
**자동화 수준**: 반자동 (3회 자동 복구 실패 시 Human Gate)
**우선순위**: P0 (최우선)

## 트리거

### 자동 트리거
- **operations 파이프라인 에러 감지**
  - 헬스체크 실패 (3회 연속)
  - 에러율 5% 초과
  - 응답 시간 2배 증가 (P95 >1초)
- **Cloudflare 알림**
  - Worker 에러 급증
  - D1 연결 실패
  - Rate Limit 초과
- **외부 모니터링**
  - 업타임 체크 실패 (Pingdom, UptimeRobot)

### 수동 트리거
- Operator 수동 실행
- 고객 신고 (긴급 티켓)

## 단계

### 1. 장애 감지 및 분류 (자동, 1분)
**AI 에이전트**: `debugger`

**입력**
- 에러 로그
- 헬스체크 결과
- 메트릭 (응답 시간, 에러율)

**작업**
1. **장애 심각도 평가**
   - **P0 (Critical)**: 전체 플랫폼 다운, 10개 이상 테넌트 영향
   - **P1 (High)**: 개별 테넌트 서비스 불가, 데이터 손실 위험
   - **P2 (Medium)**: 성능 저하, 일부 기능 제한
   - **P3 (Low)**: 경고 수준, 서비스는 정상

2. **영향 범위 분석**
   - 영향받는 테넌트 수
   - 영향받는 기능 (API, 특정 스킬 등)
   - 예상 고객 영향 (사용 시간대 고려)

3. **근본 원인 가설**
   - 로그 패턴 분석
   - 최근 배포 이력 (1시간 내)
   - 외부 의존성 (Cloudflare 상태, 외부 API)

**산출물**
- 인시던트 티켓 (D1 생성)
```json
{
  "incident_id": "INC-2026-02-08-001",
  "severity": "P1",
  "status": "detected",
  "affected_tenants": ["tenant-abc", "tenant-xyz"],
  "hypothesis": "D1 connection timeout",
  "detected_at": "2026-02-08T14:30:00Z"
}
```

**알림**
- **P0/P1**: Slack + 이메일 + SMS (즉시)
- **P2/P3**: Slack (5분 이내)

### 2. 자동 복구 시도 (자동, 3회 반복, 각 3분)
**AI 에이전트**: `build-fixer`, `executor`

**입력**
- 인시던트 티켓
- 근본 원인 가설

**작업**

#### 복구 전략 (우선순위 순)

**1차 시도: 재시작**
- Worker 재배포
- D1 연결 풀 리셋
- 캐시 무효화 (KV)

**2차 시도: 롤백**
- 최근 배포 롤백 (1시간 내 배포가 있었다면)
- 설정 변경 취소

**3차 시도: 리소스 확장**
- Worker 인스턴스 증가
- D1 연결 수 증가
- Rate Limit 임시 완화

**각 시도 후 검증**
- 헬스체크 재실행 (30초 후)
- 에러율 확인 (<1%)
- 응답 시간 확인 (<500ms)

**산출물**
- 복구 시도 로그
- 성공/실패 상태

### 3. R2 백업 복원 (자동/반자동, 10분)
**AI 에이전트**: `executor`

**조건**
- 자동 복구 3회 실패
- 데이터 손실 감지 (D1 쿼리 에러)

**작업**
1. **백업 선택**
   - 최신 백업 (24시간 이내)
   - 무결성 검증

2. **임시 환경 복원**
   - 새 Worker 인스턴스 생성
   - 백업에서 D1 복원
   - 헬스체크

3. **트래픽 전환**
   - DNS 라우팅 변경 (임시 환경으로)
   - 기존 환경 격리 (디버깅용 보존)

**산출물**
- 복원 완료 상태
- 임시 환경 URL

**Human Gate**
- 데이터 불일치 위험 (백업 시점 이후 데이터 손실)
- 프로덕션 트래픽 전환 승인

### 4. 에스컬레이션 및 수동 복구 (수동, 30분-2시간)
**AI 에이전트**: `debugger`, `executor`

**조건**
- 자동 복구 3회 실패
- R2 백업 복원도 실패
- P0 인시던트

**작업**
1. **Operator 호출**
   - SMS + 전화 (P0)
   - Slack 맨션 (P1)

2. **상세 분석**
   - 전체 로그 분석 (1시간 범위)
   - Cloudflare 상태 확인 (공식 상태 페이지)
   - 외부 API 상태 (카카오, 슬랙 등)

3. **수동 개입**
   - Operator가 직접 디버깅
   - 긴급 패치 배포
   - 필요 시 Cloudflare 지원 요청

**산출물**
- 근본 원인 (확정)
- 수동 복구 조치 내역

### 5. 고객 안내 (자동/반자동, 5분)
**AI 에이전트**: `writer`

**타이밍**
- **장애 발생 즉시**: 인지 알림 (P0/P1)
- **복구 시도 중**: 진행 상황 업데이트 (15분마다)
- **복구 완료**: 완료 알림

**작업**
1. **영향받는 고객 식별**
   - 인시던트 영향 범위 기반
   - 고객 연락처 수집 (이메일, 슬랙 채널)

2. **알림 메시지 생성**
   ```markdown
   [OpenClaw 장애 알림]

   안녕하세요, OpenClaw 운영팀입니다.

   현재 일부 서비스에 지연이 발생하고 있습니다.
   - 발생 시각: 2026-02-08 14:30 (UTC)
   - 영향 범위: API 응답 지연
   - 예상 복구: 15:00 (UTC)

   복구 작업을 진행 중이며, 진행 상황을 지속 업데이트하겠습니다.
   불편을 드려 죄송합니다.
   ```

3. **멀티채널 발송**
   - 이메일 (모든 영향 고객)
   - 슬랙 (연동된 고객)
   - 대시보드 배너 (테넌트 로그인 시 표시)
   - 상태 페이지 (status.openclasw.cloud)

**산출물**
- 고객 알림 로그

**Human Gate**
- P0 인시던트 메시지 (Operator 검토 후 발송)
- 보상 정책 (SLA 위반 시)

### 6. 복구 검증 (자동, 10분)
**AI 에이전트**: `qa-tester`

**입력**
- 복구 조치 완료 상태

**작업**
1. **기능 테스트**
   - 전체 헬스체크 (모든 테넌트)
   - 핵심 시나리오 (로그인, 대화, 스킬 호출)
   - 연동 검증 (카카오톡, 슬랙 등)

2. **성능 테스트**
   - 응답 시간 정상화 확인
   - 처리량 확인 (pre-incident 수준)

3. **데이터 무결성**
   - D1 쿼리 정상
   - 대화 히스토리 보존 확인

**산출물**
- 검증 리포트
- 복구 확정 여부

### 7. 포스트모템 작성 (자동/반자동, 30분)
**AI 에이전트**: `writer`, `debugger`

**타이밍**
- 복구 완료 후 24시간 이내

**작업**
1. **타임라인 재구성**
   - 장애 발생 시각
   - 감지 시각
   - 복구 시도 이력
   - 최종 복구 시각

2. **근본 원인 분석**
   - 기술적 원인 (코드 버그, 리소스 부족 등)
   - 프로세스 원인 (배포 절차, 모니터링 부족 등)

3. **영향 평가**
   - 영향받은 고객 수
   - 다운타임 (분 단위)
   - 비즈니스 영향 (예: 손실 거래)

4. **재발 방지 대책**
   - 즉시 조치 (Hot Fix)
   - 단기 조치 (1주일 내, 예: 모니터링 강화)
   - 장기 조치 (1개월 내, 예: 아키텍처 개선)

5. **포스트모템 문서**
   ```markdown
   # 인시던트 포스트모템: INC-2026-02-08-001

   ## 요약
   - 발생일시: 2026-02-08 14:30 UTC
   - 복구일시: 2026-02-08 15:15 UTC
   - 다운타임: 45분
   - 영향: 2개 테넌트 (전체의 1.3%)

   ## 타임라인
   - 14:30: D1 연결 타임아웃 시작
   - 14:32: 자동 감지 (헬스체크 실패)
   - 14:35: 1차 복구 시도 (Worker 재시작) → 실패
   - 14:40: 2차 복구 시도 (롤백) → 실패
   - 14:45: 3차 복구 시도 (리소스 확장) → 실패
   - 14:50: Operator 에스컬레이션
   - 15:00: 근본 원인 확인 (D1 쿼리 비효율)
   - 15:10: 긴급 쿼리 최적화 패치 배포
   - 15:15: 복구 확인

   ## 근본 원인
   특정 테넌트의 대용량 쿼리가 D1 연결 풀을 고갈시킴.
   해당 테넌트는 지식 베이스에 10만 건의 문서를 업로드했으나,
   인덱스가 없어 Full Table Scan 발생.

   ## 재발 방지 대책
   - [즉시] 해당 테넌트에 인덱스 추가
   - [1주일] D1 연결 풀 모니터링 알림 추가
   - [1개월] 대용량 업로드 시 자동 인덱스 생성
   ```

6. **공유**
   - 팀 내부 (전체 공개)
   - 고객 (요청 시, 민감 정보 제외)

**산출물**
- 포스트모템 문서 (R2 저장, Wiki 공유)

**Human Gate**
- P0 인시던트 포스트모템 (Operator 검토 필수)
- 고객 공개 여부

## 복구 전략 매트릭스

| 증상 | 1차 시도 | 2차 시도 | 3차 시도 | 에스컬레이션 |
|------|---------|---------|---------|------------|
| Worker 에러 | 재시작 | 롤백 | 리소스 확장 | 수동 디버깅 |
| D1 연결 실패 | 연결 풀 리셋 | 롤백 | R2 백업 복원 | Cloudflare 지원 |
| 응답 지연 | 캐시 무효화 | 리소스 확장 | CDN 설정 조정 | 아키텍처 분석 |
| 외부 API 장애 | 재시도 | 대체 엔드포인트 | Fallback 모드 | 외부 업체 컨택 |

## 데이터 플로우

```
[에러 감지] (operations 파이프라인)
    ↓
[장애 분류]
  ├─ 심각도 (P0/P1/P2/P3)
  ├─ 영향 범위
  └─ 근본 원인 가설
    ↓
[자동 복구 루프] (최대 3회)
  ├─ 1차: 재시작
  ├─ 2차: 롤백
  └─ 3차: 리소스 확장
    ↓ (각 시도 후)
  [검증] → 성공? → [복구 완료]
            ↓ (실패)
          [다음 시도]
    ↓ (3회 실패)
[R2 백업 복원]
    ↓ (실패 시)
[Operator 에스컬레이션]
    ↓
[수동 복구]
    ↓
[복구 검증]
    ↓
[고객 알림: 복구 완료]
    ↓
[포스트모템 작성] (24시간 이내)
```

## 성공 메트릭

### 복구 속도
- **자동 복구율**: 80% (3회 내 해결)
- **평균 복구 시간**: 15분 (자동), 1시간 (수동)
- **MTTR (Mean Time To Recovery)**: 20분

### 장애 빈도
- **월간 인시던트**: <10건 (목표: <5건)
- **P0 인시던트**: <1건/월

### 고객 영향
- **평균 영향 고객**: 2개 테넌트/인시던트
- **SLA 위반**: <2회/월

## 에러 처리

### 자동 복구 실패
- 3회 시도 후 즉시 에스컬레이션
- Operator에게 전체 컨텍스트 전달 (로그, 시도 이력)

### 백업 복원 실패
- 2세대 이전 백업 시도
- 최악의 경우: 새 환경 프로비저닝 + 고객에게 사과

### 고객 알림 실패
- 다중 채널 재시도 (이메일 → Slack → SMS)
- 실패 시: 수동 전화 (P0만)

## 최적화 전략

### 자동 복구율 향상
- 머신러닝 기반 근본 원인 예측
- 복구 전략 자동 선택 (로그 패턴 학습)

### 감지 시간 단축
- 헬스체크 주기 단축 (5분 → 1분, 리소스 허용 시)
- 이상 징후 사전 감지 (에러율 증가 추세)

### 영향 범위 최소화
- 테넌트 격리 강화 (한 테넌트 장애가 다른 테넌트에 영향 없도록)
- Circuit Breaker 패턴 (외부 API 장애 전파 방지)

## 통합

### 입력 (from)
- **operations**: 장애 감지 트리거
- **Cloudflare**: 플랫폼 알림
- **고객**: 신고 티켓

### 출력 (to)
- **customer-success**: 영향 고객 리스트 (follow-up)
- **Operator**: 에스컬레이션, 포스트모템
- **D1**: 인시던트 티켓, 로그

### 사용 서비스
- **Cloudflare Workers**: 복구 스크립트
- **Cloudflare D1**: 인시던트 티켓 DB
- **Cloudflare R2**: 백업, 포스트모템 저장
- **외부**: Slack, SendGrid, Twilio (SMS)

## 보안

### 인시던트 정보 보호
- 고객 데이터 익명화 (로그, 포스트모템)
- 민감 정보 마스킹 (API 키, 토큰)

### 백업 복원 권한
- 프로덕션 백업 복원은 Operator 승인 필요
- 감사 로그 (누가, 언제, 어떤 백업 복원)

## SLA 정책

### 다운타임 보상
- **99.9% SLA 위반** (월간 43분 초과 다운타임)
  - Basic: 1주일 무료 연장
  - Pro: 1개월 10% 환불
  - Enterprise: 1개월 50% 환불

### 데이터 손실
- **제로 톨러런스**: 데이터 손실 발생 시 무조건 보상
- 복구 불가능 시: 전액 환불 + 6개월 무료

## 교육

### 정기 훈련
- 월 1회 장애 시뮬레이션 (Chaos Engineering)
- 자동 복구 시나리오 테스트

### 런북 유지보수
- 각 장애 유형별 런북 (단계별 체크리스트)
- 포스트모템 기반 런북 업데이트
