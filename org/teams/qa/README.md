# QA 팀 (품질관리팀)

## 미션
코드 품질 관리, 테스트 커버리지 확보, TDD 프로세스 운영을 통해 안정적이고 신뢰할 수 있는 서비스 제공

## 소속 에이전트

| ID | 이름 | Claude Agent | 모델 | 역할 |
|----|------|-------------|------|------|
| A-QA-001 | TDD 엔지니어 | test-engineer | Sonnet | TDD 프로세스 관리 및 테스트 전략 수립 |
| A-QA-002 | 코드 리뷰어 | code-reviewer | Opus | 코드 품질 검증 및 리뷰 기준 관리 |
| A-QA-003 | 품질 검증자 | qa-tester | Sonnet | 통합 테스트, 성능 테스트, 보안 검증 |

## 담당 파이프라인
- **P-009: 품질 관리 파이프라인**

## 주요 업무

### TDD 엔지니어 (A-QA-001)
- TDD(Test-Driven Development) 프로세스 설계 및 운영
- 테스트 커버리지 모니터링 및 개선
- 단위 테스트(unit test) 작성 가이드라인 정의
- 테스트 프레임워크 선택 및 유지보수 (vitest, @cloudflare/vitest-pool-workers)
- CI/CD 테스트 자동화 파이프라인 관리
- 모든 PR 검수 시 테스트 커버리지 검증

### 코드 리뷰어 (A-QA-002)
- 모든 PR에 대한 코드 품질 검증
- 코드 리뷰 기준 및 체크리스트 유지
- 설계 패턴, 성능, 보안 관점 검토
- 기술 부채 추적 및 리포팅
- TypeScript strict mode 준수 확인
- 린트 규칙(ESLint) 및 포매팅(Prettier) 준수 확인

### 품질 검증자 (A-QA-003)
- 통합 테스트(integration test) 및 엔드-투-엔드 테스트(e2e test) 실행
- 성능 테스트 및 병목 분석
- 보안 취약점 스캔 (SAST/DAST)
- 회귀 테스트 자동화
- 브라우저 호환성 검증
- 인시던트 발생 시 근본 원인 분석 및 테스트 케이스 추가

## 품질 기준

### 커버리지
- **최소 기준**: 80% 코드 커버리지 (라인 기준)
- **이상적 기준**: 85% 커버리지 + 주요 경로 100% 커버
- **커버리지 미달**: 머지 차단 (자동 CI/CD)

### 테스트 작성 원칙
1. **RED → GREEN → REFACTOR**: 모든 새 기능은 반드시 테스트 먼저 작성
2. **단위 테스트**: 함수/메서드별 독립적 테스트
3. **통합 테스트**: 모듈 간 상호작용 검증
4. **엔드-투-엔드 테스트**: 전체 워크플로우 검증

### PR 리뷰 기준
- 모든 PR은 QA 팀의 리뷰 통과 필수
- 테스트 코드 필수 (새 기능, 버그 수정)
- 커버리지 감소는 차단
- 타입 오류 0개 (TypeScript strict mode)
- 린트 경고 0개

### 성능 기준
- Workers CPU 시간: 50ms 이하 (최대)
- API 응답 시간: 1초 이내 (p99)
- 빌드 시간: 5분 이내

### 보안 기준
- 취약점 스캔: 심각(Critical) 0개
- 의존성 취약점: High 이상 30일 내 수정
- 시크릿 관리: 하드코딩 금지 (자동 검사)

## 사용 도구 및 프레임워크

### 테스트 프레임워크
- **vitest**: 메인 테스트 프레임워크 (빠른 속도, TypeScript 지원)
- **@cloudflare/vitest-pool-workers**: Cloudflare Workers 환경 테스트
- **@testing-library/react**: React 컴포넌트 테스트 (필요시)

### 코드 품질 도구
- **ESLint**: 린트 규칙 검사
- **Prettier**: 코드 포매팅
- **TypeScript**: strict mode 활성화
- **SonarQube**: 코드 복잡도 분석 (선택)

### 보안 검사 도구
- **Dependabot**: 의존성 취약점 스캔
- **SAST**: 정적 코드 분석
- **git-secrets**: 커밋 전 시크릿 검사

## Human Gate 조건

**다음 경우 Operator 승인 필수**

- 테스트 커버리지 기준 완화 (80% 이하로 인정)
- 보안 취약점 일시적 허용 (CVE 등)
- 성능 기준 이탈 (응답 시간 2배 이상)
- 중요 모듈의 테스트 커버리지 미달 (P0/P1 기능)
- 기술 부채 적립 (테스트 미작성 코드 머지 결정)

## 협업 팀

### 의존 관계
- **모든 팀**: 코드 변경 시 QA 검증 필수
- **platform**: 빌드/배포 파이프라인 관리 협력
- **operations**: 인시던트 발생 시 테스트 케이스 추가

### 협업 플로우
```
개발 팀 (모든 팀)
  ↓
[A-QA-001] 테스트 작성 가이드 제공
  ↓
개발자: RED → GREEN → REFACTOR 실행
  ↓
[A-QA-002] PR 코드 리뷰
  ↓
[A-QA-003] 통합/성능/보안 검증
  ↓
All checks pass → Merge
```

## 워크플로우 예시

### 새 기능 개발 (TDD)

```
Feature 요구사항 수신
  ↓
[A-QA-001] 테스트 케이스 정의
  ↓
개발자: 테스트 작성 (RED)
  ↓
개발자: 최소 기능 구현 (GREEN)
  ↓
개발자: 코드 리팩토링 (REFACTOR)
  ↓
[A-QA-001] 커버리지 검증 (80% 이상 확인)
  ↓
[A-QA-002] PR 리뷰 (설계, 성능, 보안)
  ↓
[A-QA-003] 통합 테스트 실행
  ↓
All pass → Merge → Production Deploy
```

```
버그 리포트 수신
  ↓

  ↓
[A-QA-001] 테스트 커버리지에 추가
  ↓
개발자: 버그 수정
  ↓
[A-QA-003] 회귀 테스트 실행 (버그 재발 방지)
  ↓

  ↓

```

  ↓

  ↓

  ↓

  ↓
[A-QA-003] 성능 테스트 재실행 (개선 확인)
  ↓

  ↓

## 측정 지표 (Metrics)

### 품질 지표
- **Code Coverage**: 월간 추이 (목표 85%)
- **Bug Detection Rate**: 코드 리뷰 단계에서 발견한 버그 수
- **Time to Fix**: 버그 발견 후 수정까지 평균 시간
- **Regression Rate**: 패치 후 재발 버그 비율 (목표 0%)

### 프로세스 지표
- **PR Review Cycle Time**: PR 제출부터 승인까지 평균 시간 (목표 4시간)
- **Test Execution Time**: 전체 테스트 스위트 실행 시간 (목표 < 5분)
- **Build Success Rate**: CI/CD 빌드 성공 비율 (목표 99%)

### 팀 지표
- **커버리지 달성도**: 기준 이상 파일 비율
- **리뷰 효율성**: 리뷰어당 PR 처리 수
- **기술 부채**: 테스트 미작성 모듈 수
